## Three boundaries to keep

### 1. Identity belongs to User Service

Game verifies the access token through private `GET /auth/principal`. A missing/invalid identity is rejected. A verification outage is unavailable, not proof of a logout. Account and Arena use the same shared browser module; access tokens are not put in local storage.

<Endpoint id="principal-api" method={"GET"} path={"/auth/principal"} summary={"Private User Service verification used by Game"} auth={"Bearer access token"} description={"Returns userId and expiresAt in milliseconds after verifying token and account. Public calls, if used, pass through the /api prefix."} responses={[{"status": "200", "description": "Verified principal and token expiry."}, {"status": "401", "description": "Invalid or expired access token, or missing account."}]} />

### 2. Only the server accepts a game command

The browser sends an action once. It does not replay a mutation after auth recovery. Game checks membership, current state and input. A same-user token change reattaches sockets and reads fresh state; an account change retires the old Match scope.

### 3. Ownership comes before recovery

A second Game process using the same database must stop before recovering Matches or accepting traffic. Ownership loss closes admission and output and starts a bounded stop. This is an operating constraint, not unfinished multi-server work.
